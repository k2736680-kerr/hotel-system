# 酒店管家第三方审查报告

> 审查日期：2026-06-30  
> 审查范围：单酒店、单机、离线 Windows 前台管理  
> 审查结论：核心前台流程已形成闭环，可进入用户验收；不应宣称为多门店或联网型企业 PMS

## 1. 参照范围

审查参考了同类 PMS 对核心能力的公开说明：

- [Oracle OPERA Cloud 用户指南](https://docs.oracle.com/cd/E81346_01/doc.183/e81527/toc.htm)将预订入住、前台、客房维护和收银财务作为相互关联的业务模块。
- [Hotelogix PMS 功能说明](https://www.hotelogix.com/hotel-management-software)列出的基础能力包括预订、前台入住、客房状态、账单和经营分析。
- [Hotelogix 报表说明](https://www.hotelogix.com/reports)强调入住率、每日收入、支付、客户历史和客房状态报表。
- [鲸飞云 PMS](https://www.hanwuxi.cn/)将预订、入住、续住、换房和退房列为前台高频流程。

本项目是单机离线版，因此没有照搬渠道管理、云支付、多店、移动端等联网能力，而是检查单机前台是否具备完整且可追溯的业务闭环。

## 2. 审查时发现并已修复的问题

| 问题 | 风险 | 处理结果 |
| --- | --- | --- |
| 缺少预订、取消和预订转入住 | 无法处理电话预订和到店流程 | 已实现，含时间冲突校验和取消退定金 |
| 缺少续住和换房 | 在住期间常见操作无法入账 | 已实现，含后续预订冲突和分段房费 |
| 换房同日计价选择未持久化 | 退房重算可能改变用户选择 | 已增加数据库版本 2 迁移并持久化 |
| 缺少同住人 | 入住登记不完整 | 已实现人数上限、黑名单和主住人保护 |
| 错误费用/收款无法纠正 | 账单只能越改越错 | 已实现费用作废和关联原收款退款，保留原流水 |
| 自闭合组件导致表格列错误嵌套 | 页面列头错乱 | 已统一改为显式闭合标签并逐页截图复查 |
| 房间有预订时仍可报修 | 预订到店后无房可住 | 已禁止有有效订单的房间报修或停用 |
| 数据恢复只替换文件、不执行迁移 | 旧备份恢复后可能不能运行 | 已增加结构迁移、完整性和外键检查，失败自动回退 |
| 可同时启动多个实例 | 两个进程可能互相覆盖单机数据库 | 已增加单实例锁，第二次启动聚焦原窗口 |
| 缺少经营查询 | 无法核对营业数据 | 已增加每日入住、退房、房费、其他费用、收退款和 CSV 导出 |
| 缺少业务默认值 | 每单重复填写 | 已增加酒店名称、默认押金和入住/退房时间设置 |

## 3. 当前功能覆盖

### 3.1 已覆盖的交付范围

- 房型、房间、房价、启停、清洁和维修。
- 客户档案、身份证校验、证件去重、黑名单和脱敏显示。
- 预订、预收定金、房间时段锁定、取消、退款、预订转入住。
- 直接入住、按夜房费、押金和支付方式。
- 同住人、续住、换房、分段房间轨迹和同日计费规则。
- 手工费用、优惠限制、费用作废、收款和原流水关联退款。
- 退房补收/退款、账目结清、房间自动转待清洁。
- 每日经营报表和带 UTF-8 BOM 的 CSV 导出。
- SQLite 持久化、事务、数据库迁移、操作日志、自动/手动备份和恢复。
- 完全离线资源、安全 IPC、单实例运行和 NSIS 安装包。

### 3.2 明确不在本单机版范围

- 多台电脑同时操作、局域网或云同步。
- OTA 渠道直连、在线支付、电子发票、公安旅业上传。
- 身份证读卡器、门锁制卡、打印机和其他硬件接口。
- 多门店、复杂会员营销、餐饮 POS、库存。
- 已支持单个管理员账号注册、登录和改密；暂不支持多个操作员及管理员/前台/财务的细分权限矩阵。
- 数据库字段加密和商业代码签名证书。

如果实际使用场景包含以上任意一项，应先扩展架构，不能用共享 SQLite 文件代替服务器。

## 4. 自动化验收覆盖

当前自动化测试包含 17 组场景：

1. 日历夜数和当天入住退房最少一夜。
2. 房间、客户持久化及重复数据拦截。
3. 入住、收款、退房、退款和清洁闭环。
4. 备份与恢复。
5. 预订锁房、重叠冲突、取消和定金退款。
6. 预订转入住及续住冲突。
7. 换房房态、房间轨迹和分段房费。
8. 同住人数限制和主住人保护。
9. 错身份证、黑名单、过量优惠和错误结算金额。
10. 系统设置和经营报表。
11. 有预订时禁止停用和报修。
12. 损坏备份拒绝恢复且当前数据不受影响。
13. 混合流程后的订单、房间和活动房段全局一致性。
14. 错误费用作废、部分退款和超额退款拦截。
15. 管理员注册、登录、密码哈希和修改密码。
16. 操作日志按日期筛选、操作人记录和分页。
17. 旧版数据库升级后业务数据保留并进入首次账号注册。

此外执行了：

- 所有 JavaScript 文件语法检查。
- 房态、预订、报表、设置页面实际启动和截图检查。
- 生产依赖安全审计。
- Electron 解包应用启动检查。
- NSIS 安装包构建和打包后启动检查。
- 在 Windows 当前用户目录真实静默安装，从安装目录启动后再执行卸载；安装、启动和卸载均成功。
- 从 1.1.0 覆盖安装到 1.2.0 后，原房间数据仍存在；旧数据库自动迁移，滚动自动备份保持为一份。

## 5. 用户验收建议

交付前使用一套专门的测试数据，至少手工完成：

1. 创建两个房型、三间房和三位客户。
2. 创建明日预订并收定金；尝试同房同时间再预订，确认被阻止。
3. 取消预订，核对定金退款流水。
4. 新建预订并转入住，添加同住人、费用和收款。
5. 续住；再创建冲突预订后尝试续住，确认被阻止。
6. 换房，核对原房待清洁、新房入住中及两段房间轨迹。
7. 作废一条错误费用，对一笔收款做部分退款。
8. 退房，核对补收/退款、订单已退房和新房待清洁。
9. 标记清洁后确认房间恢复空闲。
10. 核对经营报表，导出 CSV。
11. 备份、增加测试数据、恢复备份，确认新增数据消失且原数据恢复。
12. 关闭并重启应用，确认所有数据仍在。

## 6. 交付判断

在“单酒店、单机、离线、由受控前台电脑使用”的产品边界内，当前版本具备可交付的核心流程。建议用户完成第 5 节手工验收后再发给实际使用方。

安装包目前没有商业数字签名证书，Windows SmartScreen 可能提示来源未知；这不影响离线功能，但正式对外大规模分发前建议购买代码签名证书。
