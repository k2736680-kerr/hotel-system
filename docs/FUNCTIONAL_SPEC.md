# 酒店管家功能需求与业务逻辑说明书

> 文档版本：V1.0  
> 适用项目：`hotel-crm-local`  
> 产品形态：Windows 单机离线桌面应用  
> 当前目标：先完成可可靠使用的单店前台管理闭环，再考虑联网、多门店和云同步

## 1. 产品定位

本系统用于小型酒店、民宿或公寓前台，在一台 Windows 电脑上完成房间、预订、入住、在住、退房、收退款、客户档案、经营查询和数据备份。

首个正式版本必须满足以下原则：

1. 不联网也能正常启动和使用，不能依赖 CDN。
2. 关闭软件或重启电脑后，业务数据不能丢失。
3. 房态、订单、账务必须由同一业务操作同步更新，不能只改页面显示。
4. 所有金额变化都保留流水，不允许通过直接改订单总额掩盖过程。
5. 关键操作可追溯，可通过备份文件恢复。
6. 最终交付为可双击安装的 Windows 安装程序，并可从桌面快捷方式启动。

### 1.1 当前版本边界

V1 采用以下明确边界：

- 单酒店、单机数据库。
- 可设置多个操作员，但同一时刻主要在一台电脑上使用。
- 暂不提供手机端、网站端、微信预订、公安旅业接口、门锁/身份证读卡器、发票平台、渠道直连和多店同步。
- 不做餐饮、库存和复杂会员营销。
- 允许手工录入现金、微信、支付宝、银行卡等线下支付结果，但软件本身不直接发起在线支付。

## 2. 当前项目评估

当前项目已有 Electron 桌面窗口和房间、客户、入住记录三个基础页面，可作为界面原型，但不能作为可交付版本直接使用。

### 2.1 已具备的内容

- Electron 启动本地 `index.html`。
- 房间列表和新增房间入口。
- 客户新增和客户列表。
- 选择客户后办理入住。
- 入住记录列表和退房入口。

### 2.2 关键缺失与现有错误

| 级别 | 问题 | 影响 |
| --- | --- | --- |
| 阻断 | 房间、客户、记录仅存放在 Node.js 内存数组 | 每次退出程序后数据全部丢失 |
| 阻断 | 入住和退房只在页面内存修改房态 | 刷新或重新加载后房态恢复，可能重复入住 |
| 阻断 | 入住记录没有生成稳定的 `id` | 退房使用 `row.id`，实际会得到 `undefined`，可能报错或改错记录 |
| 阻断 | 退房接口直接访问数组下标且不校验对象 | 非法记录号会导致服务异常 |
| 高 | Vue 和 Element Plus 从公网 CDN 加载 | 离线环境下界面无法启动 |
| 高 | 没有预订、续住、换房、账单、支付和退款 | 无法形成酒店前台完整闭环 |
| 高 | 没有事务和冲突校验 | 同一房间可能出现多个有效入住单 |
| 高 | 固定使用本地 19998 端口 | 存在端口冲突、防火墙和接口暴露风险 |
| 高 | `nodeIntegration=true` 且关闭上下文隔离 | 页面脚本可直接获得 Node 权限，安全边界不足 |
| 中 | 房型直接写在房间记录中 | 房型价格调整和统一维护困难 |
| 中 | 没有输入格式、重复身份证、重复房号等校验 | 数据容易重复或无效 |
| 中 | 金额和时间使用自由文本/浮点数 | 容易产生精度、排序和统计错误 |
| 中 | 无备份、恢复、日志和数据库迁移机制 | 出现故障后无法恢复或定位问题 |

结论：当前代码应视为演示原型。正式版本需要保留视觉方向，重建数据存储、领域模型和业务操作。

## 3. 是否区分前后端

### 3.1 结论

**代码职责必须区分“前端界面”和“本地业务/数据层”，但部署时不需要拆成独立前后端。** 所有代码、前端资源和数据库驱动一起打包到 Electron 应用中，用户只安装一个程序。

不建议正式版本继续启动 Express 并监听 `127.0.0.1:19998`。单机应用可通过 Electron IPC 调用主进程服务，无需占用网络端口。

### 3.2 推荐结构

```text
Electron 主进程
├─ 窗口与应用生命周期
├─ IPC 接口（只暴露允许的业务命令）
├─ 业务服务层
│  ├─ 房态与房间服务
│  ├─ 预订/入住/退房服务
│  ├─ 账务与支付服务
│  └─ 备份、设置、日志服务
├─ 数据访问层
└─ SQLite 本地数据库

Electron 渲染进程
├─ 页面、表格、表单和弹窗
├─ 输入校验与交互状态
└─ 通过 preload 暴露的安全 API 调用主进程
```

技术约束：

- 渲染进程设置 `nodeIntegration: false`、`contextIsolation: true`。
- 使用 `preload.js` 和 `contextBridge` 暴露最小 API。
- Vue、Element Plus、字体和图标全部安装到项目并打包，不从公网加载。
- 使用 SQLite 持久化；数据库文件放在 Electron `app.getPath('userData')` 下，不能放安装目录。
- 金额在数据库中以“分”为单位保存为整数，页面显示时转换为元。
- 时间以 ISO 8601 格式保存，界面按本地时区显示。
- 一次入住、换房、退房或收退款涉及的多项写入必须放在同一个数据库事务中。

## 4. 用户角色与权限

V1 至少提供以下角色；若首期只配置一个账号，该账号默认为管理员。

| 角色 | 权限 |
| --- | --- |
| 管理员 | 全部功能、账号管理、房型房间维护、价格和业务参数、备份恢复、数据导出 |
| 前台 | 预订、入住、在住服务、退房、客户查询、收退款；不能恢复数据库和删除基础数据 |
| 财务/查询 | 查看账单、支付流水和经营报表，可导出；默认不能修改业务单据 |

要求：

- 首次运行引导创建管理员账号。
- 密码只保存安全哈希，不保存明文。
- 登录成功后记录操作员；锁屏或退出登录不关闭程序。
- 所有新增、修改、取消、换房、退款、恢复备份操作记录操作人和时间。

## 5. 核心数据模型

以下实体是完整业务闭环的最小集合。

### 5.1 酒店与系统设置 `hotel_settings`

- 酒店名称、地址、联系电话。
- 默认入住时间、默认退房时间。
- 计费规则、默认押金、货币符号。
- 订单编号前缀、是否允许负库存/超售（V1 固定不允许）。
- 数据库版本、应用配置版本。

### 5.2 操作员 `users`

- 主键、用户名、显示名、密码哈希、角色、启用状态。
- 创建时间、最后登录时间。

### 5.3 房型 `room_types`

- 主键、房型名称、标准价格、默认入住人数、最大入住人数。
- 说明、排序号、启用状态。

规则：已有房间或历史订单引用的房型只能停用，不能物理删除。

### 5.4 房间 `rooms`

- 主键、唯一房号、所属房型、楼层、备注。
- 启用状态：启用/停用。
- 清洁状态：干净/待清洁。
- 维护状态：正常/维修中。

“空闲、已预订、入住中”不直接作为可随意修改的字段，而是根据有效预订和入住单计算。这样可避免房态与订单互相矛盾。

### 5.5 客户 `guests`

- 主键、姓名、证件类型、证件号码、性别、出生日期。
- 手机号、地址、备注、黑名单标记及原因。
- 创建时间、更新时间。

规则：同一证件类型和证件号码原则上唯一；再次登记时提示复用或更新原客户，不直接创建重复档案。

### 5.6 订单 `orders`

用于统一表示预约到店和直接到店入住。

- 主键、可读订单号、来源（散客/电话/线下平台/其他）。
- 联系人、联系电话、预计到店和预计离店时间。
- 订单状态：已预订/已入住/已退房/已取消/未到店。
- 预订备注、取消原因、创建人、创建时间。

### 5.7 订单房间 `order_rooms`

- 主键、订单主键、房间主键、房型主键。
- 成交日价、预计入住/离店时间。
- 实际入住/离店时间。
- 房间业务状态。

V1 页面可先限制一张订单对应一间房，但数据库模型应支持一单多房，避免后续整体重构。

### 5.8 入住人员关联 `stay_guests`

- 订单房间主键、客户主键。
- 是否主住人、登记时间。

一间房可登记多位入住人，人数不得超过房型最大入住人数；管理员可填写原因后强制保存。

### 5.9 费用明细 `charges`

- 主键、订单主键、订单房间主键（可为空）。
- 类型：房费/商品/服务/赔偿/优惠/手工调整。
- 说明、数量、单价（分）、金额（分）。
- 业务日期、创建人、创建时间、作废状态及原因。

已产生的费用不物理删除，只能作废并保留记录。

### 5.10 支付流水 `payments`

- 主键、订单主键、方向：收款/退款。
- 用途：房费/押金/其他。
- 支付方式：现金/微信/支付宝/银行卡/其他。
- 金额（分）、备注、操作人、操作时间。
- 原退款关联流水、作废状态及原因。

### 5.11 操作日志 `operation_logs`

- 操作人、操作类型、实体类型、实体主键。
- 操作摘要、变更前/后关键值、操作时间。

日志只追加，不允许在界面中修改或删除。

## 6. 状态与金额规则

### 6.1 订单状态机

```text
已预订 ──办理入住──> 已入住 ──结清退房──> 已退房
   │                    │
   ├─取消预订──> 已取消  ├─换房/续住（状态不变）
   └─逾期未到──> 未到店  └─撤销入住（限管理员且无后续账务）
```

终态订单“已退房、已取消、未到店”不能再次办理入住。如需恢复，必须由管理员执行单独的恢复操作并记录原因，或新建订单。

### 6.2 房间可办理入住条件

必须同时满足：

1. 房间处于启用状态。
2. 维护状态为正常。
3. 清洁状态为干净。
4. 当前没有状态为“已入住”的订单房间。
5. 目标时间范围内没有其他有效预订冲突。

日期冲突按半开区间判断：`新入住时间 < 已有离店时间` 且 `新离店时间 > 已有入住时间` 时冲突。前一位客人离店时间等于后一位入住时间时不视为冲突。

### 6.3 展示房态

房态优先级由高到低：

1. 停用。
2. 维修中。
3. 入住中。
4. 待清洁。
5. 今日预抵/已预订。
6. 空闲。

页面不能直接编辑“入住中”等展示房态，只能通过对应业务动作改变。

### 6.4 账务计算

- `费用合计 = 所有未作废费用明细之和`。
- `已收金额 = 有效收款之和 - 有效退款之和`。
- 押金单独统计，不计入营业收入，但参与应退金额计算。
- `待收金额 = 费用合计 - 非押金已收金额`。
- 退房时若存在未结金额，默认禁止完成；管理员可填写“挂账原因”后强制退房。
- 任何优惠必须作为负数费用明细记录，并保存原因和操作人。
- 金额输入最多两位小数且不得产生浮点计算误差。

### 6.5 房费生成规则

V1 使用按夜计费：

- 每个住宿夜生成一条房费明细，单价取订单房间成交日价。
- 当天入住当天退房，至少按 1 夜计费；管理员可用优惠或调整明细修正。
- 续住时只延长预计离店时间，不篡改已经生成的历史房费。
- 换房当天默认只收一间房的房费；系统要求操作员选择当日按原房、按新房或手工差价，并生成可追溯明细。
- 提前退房时重新计算尚未发生的房费，已确认费用通过作废/调整记录处理。

## 7. 功能模块与操作逻辑

### 7.1 登录与首次运行

首次运行：

1. 检查数据库是否存在并执行版本迁移。
2. 若无管理员，进入初始化向导。
3. 填写酒店名称、管理员账号、默认入住/退房时间和默认押金。
4. 创建数据库与管理员后进入登录页。

日常登录：

- 用户名和密码必填。
- 连续输错达到配置次数后临时锁定，并记录日志。
- 登录后进入房态总览。

### 7.2 首页/房态总览

需要展示：

- 今日预抵、今日预离、当前在住、空闲干净、待清洁、维修中数量。
- 今日收款、退款、净收款。
- 按楼层或房型展示房态卡片。
- 关键字搜索房号、客户姓名、手机号、订单号。
- 点击房间卡片打开详情和当前可执行操作。

房间卡操作：

| 当前状态 | 允许操作 |
| --- | --- |
| 空闲干净 | 新建预订、直接入住、设为待清洁、报修 |
| 今日预抵/已预订 | 查看预订、办理入住、取消预订 |
| 入住中 | 查看账单、续住、换房、加住客、加费用、收款、退房 |
| 待清洁 | 标记已清洁、报修 |
| 维修中 | 查看/结束维修 |
| 停用 | 查看详情、重新启用 |

### 7.3 房型管理

功能：新增、编辑、停用、启用、排序和查询。

校验：

- 房型名称必填且不能重复。
- 标准价格必须大于或等于 0。
- 默认入住人数至少为 1，最大入住人数不能小于默认人数。
- 修改标准价格只影响之后新建的订单，不自动修改历史订单成交价。

### 7.4 房间管理

功能：新增、编辑、停用、启用、标记清洁、报修、结束维修和查询。

校验和限制：

- 房号必填且全局唯一，保存前去除首尾空格。
- 必须选择已启用房型。
- 入住中或存在未来有效预订的房间不能停用。
- 入住中的房间不能进入维修；紧急维修必须先换房或退房。
- 有历史业务引用的房间不能删除，只能停用。

### 7.5 预订管理

新建预订流程：

1. 输入预计入住和离店时间，离店必须晚于入住。
2. 选择房型后查询可用房间；可先订房型、后分配房号，但办理入住前必须分房。
3. 填写联系人、手机号、来源、成交价和备注。
4. 可登记或选择客户，可录入预收/押金。
5. 系统再次校验时间冲突并以事务保存订单、房间和支付流水。
6. 生成唯一订单号并显示预订成功。

预订列表：

- 按订单号、联系人、手机号、日期、来源和状态筛选。
- 支持查看、编辑未入住预订、分配/更换房间、办理入住、取消和标记未到店。
- 修改日期或房间时必须重新做冲突校验。
- 取消预订必须填写原因；存在预收款时先提示退款处理。

### 7.6 客户档案

功能：新增、编辑、查询、查看历史入住、黑名单标记。

校验：

- 姓名必填。
- 证件类型和证件号办理入住时必填，普通联系人可暂不填证件。
- 中国居民身份证按长度和校验位检查；其他证件只做必填和长度检查。
- 手机号允许为空；填写时校验合理格式。
- 检测到重复证件时展示已有客户并让操作员复用，不静默覆盖。
- 身份证和手机号在列表默认脱敏，查看完整内容受权限控制并记日志。

### 7.7 直接入住/从预订入住

办理流程：

1. 从空闲房间选择“直接入住”，或从有效预订选择“办理入住”。
2. 确认房间、实际入住时间、预计离店时间和成交日价。
3. 至少登记一名主住人，可添加同住人。
4. 检查黑名单、证件重复、入住人数和房间冲突。
5. 录入押金/预收款及支付方式；允许稍后收取但需明显提示欠款。
6. 用户确认后，系统在一个事务中：创建或更新订单、关联住客、写入首期费用/支付流水、更新订单状态并记录日志。
7. 成功后房态立即变为入住中；任何一步失败均不得留下半成品数据。

从预订入住时保留原订单号、预收流水和预订来源，不重新创建互不关联的记录。

### 7.8 在住管理

在住详情包含：

- 订单、房间、入住人和预计离店信息。
- 费用明细、收退款流水、费用合计、已收、押金、待收/应退。
- 续住、换房、增加/移除同住人、添加费用、优惠调整、收款、退款、备注和退房入口。

续住：

1. 选择新预计离店时间，新时间必须晚于原离店时间。
2. 检查该房间延长时段是否与后续预订冲突。
3. 有冲突则禁止保存，并提示冲突订单；可先协调换房或修改后续预订。
4. 保存成功后补充未来房费计划并记录日志。

换房：

1. 只能选择空闲、干净、正常且目标时间无冲突的房间。
2. 选择换房时间和当日计费规则。
3. 在事务中结束原房段、创建新房段、处理房费差额并记录换房原因。
4. 原房变为待清洁，新房变为入住中。

添加费用：选择费用类型、说明、数量、单价和业务日期；优惠和手工调整要求填写原因。

收款/退款：

- 收款金额必须大于 0，选择支付方式和用途。
- 退款必须选择可退款的原收款；累计退款不得超过原收款金额。
- 非管理员退款可设置额度限制。
- 不允许直接修改已存在支付流水；错误流水走作废或冲正流程。

### 7.9 退房结算

标准流程：

1. 打开在住订单并确认实际退房时间。
2. 系统根据住宿夜、费用明细和收退款流水计算账单。
3. 展示费用合计、非押金已收、押金、待收金额和应退金额。
4. 若待收大于 0，完成收款；若应退大于 0，登记押金退款。
5. 操作员确认账目和支付方式。
6. 系统在一个事务中写入最终费用、收退款、实际离店时间，将订单改为已退房，并将房间改为待清洁。
7. 生成可打印/导出的结账单。

限制：

- 已退房订单不能重复退房。
- 有未结金额时默认不能退房。
- 退房后新增费用、退款或撤销退房仅管理员可操作，且必须填写原因。
- 房间退房后不能直接变为空闲干净，必须由保洁确认清洁完成。

### 7.10 清洁与维修

- 退房自动产生待清洁状态。
- 操作员可将待清洁房标记为已清洁，记录操作人和时间。
- 报修需填写原因、开始时间；维修期间不可预订或入住。
- 结束维修需填写处理结果，结束后默认为待清洁，由人工确认后恢复空闲。

### 7.11 账单、流水与交班

账单查询：按订单号、客户、房号、日期、订单状态查询完整费用和支付流水。

支付流水：按时间、操作员、支付方式、收款/退款筛选，显示合计。

交班功能：

- 操作员选择班次起止时间。
- 系统统计该操作员期间各支付方式的收款、退款和净额。
- 填写实收现金和差异原因后提交交班记录。
- 已提交交班记录只读，管理员可查看和导出。

### 7.12 经营报表

V1 报表：

- 每日经营汇总：入住间夜、退房数、房费、其他费用、优惠、收款、退款、净收款。
- 入住率：已售间夜 / 可售间夜；停用和维修房间不计入可售间夜。
- 房型销售：各房型间夜、收入、平均房价。
- 支付方式汇总。
- 客户入住历史。

报表支持日期筛选、页面预览和导出 CSV。CSV 使用 UTF-8 BOM，确保 Windows Excel 打开中文不乱码。

### 7.13 系统设置

- 酒店基本资料。
- 默认入住/退房时间、默认押金、计费参数。
- 订单来源、支付方式、费用类型等字典配置。
- 操作员和角色管理。
- 数据库备份、恢复、导出。
- 查看应用版本、数据库版本和操作日志。

影响历史账务的设置不得反向修改历史数据。

### 7.14 备份与恢复

备份：

- 用户可手动选择目录生成带时间戳的备份文件。
- 每次正常退出或每日首次启动时自动备份，保留最近 N 份（默认 30）。
- 备份前确保数据库事务完成，并校验备份可打开。
- 备份文件包含数据库、必要配置和版本信息，不包含明文密码。

恢复：

1. 仅管理员可执行。
2. 选择备份后先校验文件、版本和完整性。
3. 明确提示恢复会覆盖当前数据，并自动再备份当前数据库。
4. 恢复成功后重启应用；失败则保留原数据库。

## 9. 本地业务接口边界

渲染进程不直接执行 SQL。建议通过 preload 暴露按业务命名的异步方法，例如：

- `dashboard.getSummary(filters)`
- `rooms.list(filters)`、`rooms.create(data)`、`rooms.markClean(id)`
- `roomTypes.list()`、`roomTypes.save(data)`
- `guests.search(keyword)`、`guests.save(data)`
- `reservations.create(data)`、`reservations.update(id, data)`、`reservations.cancel(id, reason)`
- `stays.checkIn(data)`、`stays.extend(id, data)`、`stays.changeRoom(id, data)`、`stays.checkOut(id, data)`
- `billing.addCharge(data)`、`billing.collect(data)`、`billing.refund(data)`
- `reports.daily(filters)`、`reports.exportCsv(type, filters)`
- `backup.create()`、`backup.restore(file)`

每个调用统一返回成功数据或结构化错误：错误码、用户可读信息和可选字段错误。页面不能依赖解析数据库异常文本。

## 10. 非功能要求

### 10.1 可靠性

- 所有关键业务操作使用事务。
- 按钮提交期间禁用，防止重复点击。
- 应用异常关闭后数据库保持一致；下次启动执行完整性检查。
- 数据写入失败时页面明确提示，不能先显示成功再后台失败。

### 10.2 性能

- 1 万客户、10 万订单规模下，常用列表首次查询目标小于 1 秒。
- 客户证件、手机号、订单号、房号和业务日期建立索引。
- 大列表使用分页，不一次性加载全部历史记录。

### 10.3 安全与隐私

- 关闭渲染进程 Node 直连能力。
- IPC 参数在主进程再次校验，不能只依赖页面校验。
- 数据库和备份只写入用户数据目录或用户指定目录。
- 日志不得输出完整身份证、密码或支付敏感信息。
- 打开外部链接必须使用白名单；禁用任意页面导航。
- V1 可不做数据库加密，但需要在产品说明中明确本机文件权限边界；如保存真实身份证信息，正式商用前建议加入数据库/字段加密。

### 10.4 易用性

- 业务状态使用固定颜色和文字，不能只用颜色区分。
- 金额、时间和危险操作必须二次确认。
- 表单错误显示在具体字段旁。
- 支持常见键盘操作，保存后焦点和页面状态合理恢复。

### 10.5 兼容性

- 首期支持 Windows 10/11 x64。
- 安装路径可包含中文和空格。
- 普通用户权限可安装到用户目录并正常升级。
- 断网、无默认浏览器、端口被占用时不影响核心业务。

## 11. 安装、升级与数据目录

推荐使用 `electron-builder` 生成 NSIS 安装程序：

- 安装包包含 Electron、应用代码、前端静态资源和 SQLite 原生依赖。
- 安装时创建开始菜单和可选桌面快捷方式。
- 应用程序文件放安装目录；数据库、配置、日志、自动备份放 `%APPDATA%/<应用名>/`。
- 卸载程序默认不删除业务数据库，另提供明确的“同时删除本地数据”选项。
- 应用升级先自动备份，再执行数据库版本迁移；迁移失败则回滚并保留旧数据。
- 构建产物需要在一台未安装 Node.js 的干净 Windows 电脑上验证。

是否最终只有一个文件需要区分：交付给用户的是一个 `.exe` 安装程序；安装后会展开为应用目录和用户数据目录，这是 Electron 的正常工作方式。若强制做真正的单文件便携版，会增加数据目录、升级和杀毒软件误报方面的问题，不建议作为默认交付。

## 12. 开发优先级与版本计划

### P0：可保存且业务不出错

1. 本地化 Vue/Element Plus，重构 Electron 安全配置和 IPC。
2. 引入 SQLite、迁移机制、统一错误处理和日志。
3. 完成房型、房间、客户基础数据及严格校验。
4. 完成直接入住、在住查询、收款、退房和清洁闭环。
5. 完成账单/支付流水、事务、房态计算和冲突校验。
6. 完成备份恢复和 Windows 安装包。

P0 完成后，系统才具备保存真实业务数据的基本条件。

### P1：完整前台日常业务

1. 预订、取消、未到店、预订转入住。
2. 续住、换房、同住人、加费用、优惠、退款。
3. 首页指标、搜索、筛选和订单详情。
4. 登录、角色、操作日志、结账单导出。

### P2：经营管理

1. 交班。
2. 日报、入住率、房型销售、支付汇总。
3. CSV 导出、自动备份策略、数据完整性工具。

### 后续可选

- 打印小票、身份证读卡器、门锁制卡、公安上传、发票。
- 会员、协议客户、渠道订单、房价日历。
- 局域网多终端、云同步、多门店。

注意：一旦需要多台电脑同时操作，不能继续共享 SQLite 文件。届时应改为中心服务 + 数据库架构，并增加并发控制、账号鉴权和网络故障处理。

## 13. V1 验收标准

以下场景全部通过，才可认为 V1 功能闭环成立：

1. 安装程序可在未安装 Node.js、断网的 Windows 10/11 电脑上安装并启动。
2. 新建房型、房间和客户后退出并重启，数据仍存在。
3. 同一房号和同一证件不能被静默重复创建。
4. 空闲干净房可办理入住；入住后重启应用仍显示入住中。
5. 同一房间在重叠时间不能创建两个有效预订/入住。
6. 入住事务中任一步失败时，不产生孤立订单、错误房态或半条支付流水。
7. 在住订单可添加费用和收款，余额计算准确到分。
8. 退款不超过原收款，且能追溯到原流水。
9. 续住遇后续预订冲突时被阻止；无冲突时成功延长。
10. 换房后原房待清洁、新房入住中，账单和房间轨迹完整。
11. 退房时自动计算待收/应退；未结清时不能普通退房。
12. 退房成功后订单为已退房、房间为待清洁；标记清洁后才恢复空闲。
13. 已退房订单不能重复退房，历史费用和支付流水不能直接删除。
14. 日报收款、退款、净收款与测试流水逐笔核对一致。
15. 手动备份后新增数据，再恢复备份，数据回到备份时状态。
16. 升级应用不丢失旧数据库，迁移失败时能够回滚。
17. 普通前台无法执行恢复数据库、账号管理等管理员操作。
18. 身份证列表默认脱敏，日志中不出现密码和完整敏感证件信息。

## 14. 本文档确认项

开始大规模实现前，需要把以下产品选择固定下来；未单独调整时按本文默认值执行：

| 决策项 | 本文默认方案 |
| --- | --- |
| 使用场景 | 单酒店、单机、离线 |
| 发布方式 | Electron + NSIS 安装版 EXE |
| 代码架构 | 前端界面与本地业务层分层，单应用打包，不启动 HTTP 服务 |
| 数据库 | SQLite，数据放用户目录 |
| 订单模型 | 支持预订和直接入住，底层预留一单多房 |
| 计费 | 按夜、当天入住退房至少 1 夜、允许有痕调整 |
| 退房后房态 | 待清洁，人工确认后空闲 |
| 支付 | 记录线下支付结果，不直接对接支付平台 |
| 首发平台 | Windows 10/11 x64 |
| 多机并发 | V1 不支持 |

本文档确认后，下一步应先完成数据库设计与 P0 页面/业务接口拆分，再进入具体编码；不建议继续在当前三个内存数组和单个 `index.html` 上追加功能。
